# FC Arena startup and player workflows release design

## What players and administrators should see

Android could show a blank surface between the system splash and the first WebView frame. Within the app, the next match, tournament, and profile controls took extra scanning, and result admins had to clear multiple filters to return to the pending queue. This release covers the journey from launch through these existing player and administrator workflows.

On a cold Android launch, the existing Activity carries the official crest from the system splash into a short football-pitch animation. Home shows both teams for the next match and uses a skeleton that follows the loaded layout. Cup Center filters the current league's visible tournaments by name or code. Playoffs displays a trophy after a verified final and keeps controls readable on narrow devices. Profile section links reach photo, career, identity, and opponent contact controls. The contact badge reflects the signed-in player's saved sharing preference. Admins can reset the result queue to pending review and distinguish result status from request failures.

The original [startup design](premium-startup-design.md) and [engineering handoff](premium-startup-handoff.md) describe the earlier implementation and measurements. Review their claims as supporting evidence. The current application code and clean candidate artifacts establish the final release scope.

## System boundaries

- The cold-launch decoration belongs to `MainActivity`. The trusted `fcarena.in` HTTPS main document and WebView visual state callback govern the handoff. The decorative phase has a 1,200 ms ceiling from its first drawn frame. A delayed page gets the connecting message, then the existing retry or content states. Disabled system animations, low memory, and renderer software recovery select a static crest. The earlier Robolectric checks cover resume, Activity restoration, and stale visual callbacks. Release checks distinguish the first useful sign-in or authenticated page from an earlier splash or loading frame and include slow and failed requests.
- Web changes use existing shared styles and endpoints. Cup search filters the selected league and status already authorized by the API. A champion trophy requires a verified final. The profile badge reflects the signed-in player's saved `whatsappShareEnabled`. Resetting result filters selects `PENDING_VERIFICATION` across permitted leagues and tournaments via a read request. Existing confirmation, result submission, standings, authentication, consent authorization, and the schema remain API-owned.

## Alternatives considered

A web splash would cover every route but could start only after the first WebView frame and would add a loading layer to browser visits. The native Activity can cover the system-to-WebView transition while the web keeps its own useful loading states. A coordinated web/API switch would require two runnable rollback artifacts and a plan for partial activation. The release changes the Android shell and web behavior while keeping the existing API contract and schema. A staged web switch on the current API reduces disk use and leaves the live API source and data in place. Coordinated activation remains a separate recovery decision if parity or compatibility checks reveal a server dependency.

2. Build the locked candidate on Linux outside VCCLHosting. Record the immutable SHA and artifact checksum. Stage the production-target package on a private loopback service for release-marker and startup asset checks. In the disposable database use synthetic identities for signed-out launch, next match and Cup search, saved opponent WhatsApp consent disabled, and the pending admin queue with filter reset. Test cold open, resume, retry, and reduced motion on baseline and candidate Android debug builds using the checked-in WebView CDP harness and fixtures. The public web release uses unchanged Android request paths and the active API contract. Production Play distribution also requires the installed release build and update evidence on a physical Android device through the authorized Play track.
3. Verify current backup integrity and isolated restore. Record the backup creation time, checksum, database restore outcome, and `_prisma_migrations` names, applied checksums and any unresolved entries. Use a disconnected disposable PostgreSQL instance with a memory limit and temporary data storage. Do not run the reset-style recovery helper against a live database. The schema check passes when the current ledger matches the active API baseline and the web candidate introduces no migration change. As a separate storage audit finding, document whether an encrypted copy and approved recovery recipient exist. Verification of such a copy requires matching the encrypted artifact checksum, decrypting under authorized operator control, and proving restore.
4. Keep the rollback runtime under `/opt/fcarena/apps/web` and stage the candidate as a separate complete `.next`, `public`, Next config, package metadata and compatible node_modules reference under `/opt/fcarena-deployments`. Preserve the old static chunks in the candidate without overwriting hashed files. Under `/run/lock/fcarena-release.lock`, rehearse with the same working-directory and environment-file pointers on a separate `systemd-run` service, then switch back. Before a public switch, confirm capacity, service identities, source parity, the backup and verification evidence, and production authorization. Activate web by installing a last-ordered drop-in for `fcarena-web` with the staged `WorkingDirectory`, candidate `EnvironmentFile`, and writable Next cache, then reload systemd and restart the web unit. Keep nginx and the API unit running. Within the bounded verification window check the public home and login, `/web-release`, `/dashboard` markup and referenced chunks, and both forwarded and direct API health. On failure move the new drop-in out of the active `.conf` set, reload systemd, restart `fcarena-web`, and check the previous web marker and current API health.
5. After successful public web and API checks, the release owner or authorized operator confirms the Play track, the original upload certificate, and the highest version code used in Play Console. Follow [the release procedure](step-18-release-system.md), `apps/android/build-signed-release.ps1`, and the `Play Production Evidence Gate`. Record the signed AAB checksum, matching upload certificate, exact source SHA, installed device evidence, and Play track outcome.

### Acceptance evidence and failure handling

Before web activation, resolve review blockers, record the resolution or accepted deferral of each major finding, and capture the pinned CI, authenticated staging, reconciled sources, current backup checksum, isolated production restore, and runnable rollback rehearsal. Public health and the expected release identities verify the switch.
