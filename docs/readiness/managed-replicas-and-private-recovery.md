# Managed replicas and private PC recovery

This release uses the existing VCCLHosting machine and the owner's approved private PC. Two API processes and two web processes share the existing PostgreSQL, Redis and stable media paths. Nginx balances requests and skips failed processes. This protects against an application process failure; the physical host, database and Redis remain single points of failure. A second host needs a separate infrastructure decision.

## Runtime and release

Build with `.github/workflows/offhost-build-artifact.yml`. Verify its SHA256, rehearse the exact Linux artifact with disposable PostgreSQL 17 and Redis, real browser login, cross-instance match updates and a stopped-replica failover. Do not install or build dependencies on production. Never run `start:prod` during activation: it includes migrations.

The root-owned `/etc/fcarena/managed-release/current.json` identifies the runtime and source SHA. Root-only `api.env` and `web.env` consolidate the effective inherited service environment; the API retains `/opt/fcarena/apps/api` as its working directory for stable dotenv/media compatibility. Existing environment files and legacy drop-ins are retained. Only the primary API runs scheduled workers; both APIs share Redis request quotas and match-event pub/sub. Authentication quotas stay in PostgreSQL, and unavailable Redis acceleration falls back to the existing database budget.

`ops/release/managed_runtime.py activate --runtime <exact-runtime> --sha <40-character-source-sha> --expected-old <observed-live-sha> --staging-proof <verified-proof-json>` installs or updates the managed pointer under `/run/lock/fcarena-release.lock`. Run it as root on `fcarena-prod` only after the reviewed deployment is authorized. It requires fresh encrypted local/off-host/restore proof, unchanged schema/migrations, exact candidate staging proof, stable storage and environment parity. It bounds app memory and retains the previous version and static chunks. It never migrates the production schema. Both runtime markers must report the intended SHA.

Rollback uses `python3 /opt/fcarena-ops/release/managed_runtime.py rollback --runtime <failed-runtime>` and the root-only `managed-rollback.private.json` next to that runtime. This restores the previous pointer/units or the retained pre-managed Nginx and service drop-ins, then checks the prior exact releases. No database is restored and no releases, media or old backups are deleted. Check `https://fcarena.in/web-release`, `https://api.fcarena.in/api/health`, `npm run check:availability`, affected public pages, and the main-branch production release verifier for web and API.

## Encrypted recovery

`fcarena-encrypted-backup.timer` runs daily at 02:00 UTC with up to five minutes of jitter. The producer writes the database dump in tmpfs and streams database, persistent media and referenced Cloudinary images into a GPG-encrypted archive in `/var/backups/fcarena-encrypted`. Its embedded manifest records every file checksum and provider reference. The server has only the public encryption key. Existing plaintext archives are retained; their old scheduled producers are disabled only after a successful private PC restore.

The private folder is `C:\Users\micha\Music\FCARENAKP\.tmp-release\recovery\managed-backups`. It is excluded from Git and restricted to the owner, SYSTEM and administrators. Its recovery key passphrase uses Windows DPAPI for the current Windows user. Neither private keys nor production user data go to GitHub. Preserve this PC profile and its private recovery folder; the server's public key cannot decrypt backups.

After an initial successful `python ops/backup/pc_backup.py verify --private-directory <approved-private-folder>`, install `ops/backup/install-pc-backup-task.ps1`. The hidden task runs at sign-in and hourly while the user is signed in and connected. It downloads ciphertext through a dedicated SSH key restricted to manifest, bounded ciphertext reads and checksum receipts. It checks ciphertext SHA256 on every copy. On first use and every seven days it decrypts locally, verifies every database/media checksum, and restores into a new loopback PostgreSQL cluster. It never overwrites a local or production application database. A failed check does not acknowledge a verified restore.

`GET /api/health/backups` exposes safe freshness metadata only. Availability fails when encryption/media completeness fails or local backup exceeds 30 hours, off-host copy exceeds 48 hours, or restore proof exceeds eight days. Keep the PC online and signed in regularly. Scheduled receipt age is monitored; a powered-off PC cannot receive backups. Recovery is a verified restore workflow, not automatic failover of an entire server. Historical backups are not automatically pruned; the producer refuses to consume the final 8 GiB of disk.
